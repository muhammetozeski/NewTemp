# Configuration and portable paths

Read this before adding a setting or changing installation and data locations.

## One extensible settings registry

`Settings` defines the settings as `Setting<T>` fields. The supplied `SettingsManager` discovers those fields through reflection, assigns each field name as its key, reads `key = value` lines, and saves the same format. To add a setting, add a field with its fallback value and add semantic validation when needed. There is no separate key registration list.

Missing keys retain their initialized values. A value that cannot be converted retains its existing value; this process loads settings once, so the fallback at that point is its initializer. Unknown keys are ignored on load and are not rewritten on ordinary startup. Explicitly saving registered settings writes the recognized fields.

`Configuration.Validate` supplements the parser: `MaximumIndex <= 1` becomes `10000`; a missing, empty, relative, wildcard-containing, or invalid Windows root becomes `C:\C`. A syntactically valid custom absolute root is retained. A filesystem access failure at a valid root is reported rather than redirecting the operation to another location.

`Language` defaults to `system`. Empty, invalid, or unavailable selections fall back to `system`. `tr` and `en` use shipped resources; other valid culture codes require their own local language file. Language completeness is checked by `ApplicationServices` before normal operation.

An unavailable settings file is logged, and startup retains default values. A missing file is generated by the shared settings saver when the program folder is writable. Normal startup does not save over an existing configuration.

## Executable-relative storage

`AppConstants.ConfigFileName` points to `NewTemp.settings.txt` in `AppPaths.Root`, next to the executable. This deliberately adapts the template's default settings location to the requested layout while preserving its format and parser.

`AppPaths` uses `AppContext.BaseDirectory`, independent of the terminal working directory. A single-file distribution contains the executable and the sample configuration. Runtime-created data uses `UserData/lang.tr.xml`, `UserData/lang.en.xml`, and `AppCache/Logs` under the portable root. User sandbox items go to the external configured `RootDirectory`.

The supplied logger writes through its background queue. Console logging defaults to false so a successful call prints only the result path. Each log filename includes its process identifier to separate concurrent calls. The original queued writer has no shutdown flush protocol, so a return from `Log` does not guarantee that every queued record reached disk before process exit.

## Verification and releases

The package-free [configuration probe](../tests/ConfigurationProbe/Program.cs) consumes the production assembly through reflection rather than adding test members to production code. For v1.0.0, 26 assertions verified missing-file generation, missing and invalid roots, missing and invalid limits, invalid language fallbacks, valid values, registered settings persistence, and unknown-key tolerance. It never calls the storage creation service and therefore does not create the default sandbox root.

The integration suite ran the copied executable from a different working directory, then relocated its portable folder. It found the same configuration and language files, created the configured sandbox, and preserved the existing configuration bytes.

[Publish.ps1](../scripts/Publish.ps1) produces two Windows x64 single-file executables in `publish/` under a NewTemp scratch directory. Pass `-ScratchDirectory` to reuse a task's existing folder; otherwise the script obtains one from the installed NewTemp. Build intermediates also remain there, under `build/`. The self-contained output uses .NET 10.0.12; the framework-dependent output requires .NET 10. Both retain the same settings filename. Real user settings, logs, and cache directories are excluded from release assets.
